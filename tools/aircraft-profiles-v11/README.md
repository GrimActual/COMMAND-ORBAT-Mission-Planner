# Original Mi-8MT v1.1 evidence acceptance

`acceptance.cjs` is a local evidence validator, independent of HTTP/plan schemas, UI, occupied spawning and the native force writer. It supports only exact vanilla Mi-8MT transport, one controlling pilot and four cargo occupants. It does not install a native profile or authorize execution. Every result retains `executable:false`.

Call `evaluate(candidate, currentEnvironment, capabilityReceipts)`. Malformed non-JSON/accessor/oversized input throws; unsupported or incomplete evidence returns an unaccepted result with reasons. Inputs are copied and never mutated. Requirements and exact identity are frozen, including nested check arrays.

The candidate schema is `command-mi8-acceptance-candidate`, version 1: `profileId`, exact `identity`, `testedLoad:{pilots:1,cargo:4}`, `environment` and `calibration:{status:"native-measured",parametersSha256}`.

An environment has `kind:"installed-metadata"`, exact nonempty `gameBuild`, `controllerSourceSha256`, `installedSnapshotSha256` and `addons:[{id,version,metadataSha256}]` including base/core and all actual dependencies. Current environment also requires `installedSnapshotVerified:true` and `calibrationParametersSha256`. These are supplied only by the owning trusted local harness after checking the actual installation and accepted source, never by a request or saved mission. Fixture-provenance digests are rejected rather than relabelled as installation evidence. Addon order is insignificant; unknown, missing, changed or duplicate dependencies fail closed.

`parametersSha256` must be computed from the actual canonical native profile settings **and tested envelope**: gains/caps, RPM/readiness, cargo/load constraints, terrain/clearance limits, speed/route limits, ground/landing criteria and cancellation behavior. It is not a hash of just a profile name. The controller hash must identify the exact final shared controller source used in the accepted run. Any relevant source/settings/environment change invalidates old matching receipts. Installed metadata hashes do not certify every packed asset byte; changed same-version assets need fresh verification/native evidence.

Each capability receipt uses schema `command-aircraft-capability-evidence`, version 1, unique `evidenceId`, `capability`, `profileId`, exact `identity`, matching `environment` and `testedLoad`, `calibrationParametersSha256`, `outcome:"passed"`, `artifactSha256`, `artifactVerifiedByHarness:true`, `evidenceKind:"native-dedicated"` and `checks` containing all capability-specific required booleans. The exported `REQUIRED_CHECKS` lists those exact checks. A verified local producer derives them from actual retained native evidence and applicable numeric criteria; callers must not manufacture them from small peaks or console success. An unsafe startup or missing landing/unload/cancellation cannot become accepted because another stage passed.

These declarations and hashes are not authenticated proof. This module cannot verify an opaque artifact by itself; the owner must verify original bytes, provenance, test interpretation and the expected profile/limits before supplying a receipt. Never expose this input as a remote authorization API. No actual native passing receipt is shipped in this source directory.

Result schema version 2 separates `nativeCalibrationAccepted` (inspection, exact crew/passenger seating, safe powered startup, lift, hover, point flight, landing, unload and airborne cancellation) from `humanHandoffAccepted` and `multiplayerAccepted`. `acceptedForReviewedFlight` retains its stricter original meaning: native calibration plus native human-handoff evidence. Human and multiplayer gates may remain unverified without erasing completed isolated-native calibration. `multiplayerAccepted` requires its own `native-multiplayer` receipt. HostGM/dispatcher must still enforce approval, ownership, expiry, single lease/writer, human protection and the tested envelope on each execution.

`fullOperationalAccepted` additionally requires both `humanHandoffAccepted` and `multiplayerAccepted` alongside native calibration. It is a separate evidence summary, not runtime execution permission.

Nine focused offline acceptance tests exercise fabricated schema fixtures only: complete schema decision boundaries, absent/inherited flight evidence, environment/calibration changes, synthetic/unsafe evidence rejection, immutable JSON input/requirements and separated calibration/human/multiplayer/full-operational gates. They are not native or multiplayer proof. Run `node --test tools/aircraft-profiles-v11/acceptance.test.cjs` when relevant changes justify it.

`review-run.cjs` reads a completed or interrupted private diagnostic directory and optional current native source directory. It reduces selected facts, hashes the actual candidate controller/profile source, and reports whether those hashes match current source. Missing terminal evidence remains incomplete; `success:false` is never interpreted as an aircraft failure. `summarize-flight.cjs` filters actual controller physics records (positive bounded timestep), preserves acceleration command/response alignment and yaw wrapping, and never infers stopping distance from final arrival error. Three reducer tests and five telemetry tests passed. No raw native artifact is copied to this source directory, and neither reducer creates acceptance receipts.

The current native Mi-8 experiments and diagnostics remain private outside source. Existing engine-only startup drift is a negative result; the runtime production registry remains Huey-only until the controller owner explicitly accepts a proven Mi-8 implementation.
