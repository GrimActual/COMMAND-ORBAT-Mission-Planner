# Literal function registration and lexical call candidates

## Delivered scope

`planner/sqf-function-registrations.js` reads a bounded supplied-source set and inventories literal `CfgFunctions` declarations, proposed function source paths and lexical named call/spawn candidates. It reuses the include resolver's immutable supplied-source context and path policy. It does not preprocess includes, expand macros, merge configs, resolve inheritance, bind runtime variables, type-check calls or generate Enforce code. This is a developer core plus Node-worker CLI, not a new installed desktop feature or general converter.

Bohemia's [Functions Library documentation](https://community.bistudio.com/wiki/CfgFunctions) describes tag/category/function declaration levels and named functions. This pass recognises that literal hierarchy only. It uses a quoted tag override or the literal tag-class name; a literal function `file` or a literal category directory plus `fn_<class>.sqf`. Defaults are intentionally not guessed. Relative file properties require an explicit per-file config root; a header's containing directory is not automatically treated as the mission root. Absolute Arma paths require explicit virtual mounts. Alternative extensions, dynamic fields, duplicate fields, inheritance and opaque config statements retain blockers. Literal preInit/postInit/recompile 0/1 values are recorded as candidates and never invoked.

All supplied loose config files are inspected independently without include insertion. A CfgFunctions body split across include fragments therefore remains incomplete. Macro-generated class names are opaque, and unknown statements/preprocessor directives produce visible config findings. A zero registration count is not proof that the project registers no functions. Even a bare identifier that looks literal can be a macro token before preprocessing; proposed names retain that unresolved gate. Conditional alternatives are not selected; duplicate names stay ambiguous. Forward declarations are not registrations. Nested function classes remain blocked. The mini config reader is not a full Arma config parser, C++ parser or GNU CPP implementation.

The SQF pass records lexical adjacency after call/spawn, ignoring ordinary strings/comments and unexpanded directive bodies. Named `_fnc_` tokens can be linked to declaration-name candidates, case-insensitively. Inline code, dynamic variables and FUNC-style macros remain opaque. A keyword used as an identifier/assignment can still appear as lexical evidence; this pass does not prove an actual executed call, arity, reachable path, function value or closure. Assignments, overrides, load order, runtime compilation and source/target effects need later semantic passes. Even a unique name with an exact file match has bindingResolved:false and executionReady:false.

## Producer contract and worker

Report schema: `command-sqf-function-registration-review` version 1. Mandatory top-level non-execution/non-binding flags and review gates remain false/present. Reports carry UTF-16 source spans, decoded UTF-8 source hashes, a dependency source-set fingerprint and a domain-separated registration review-context fingerprint that also includes explicit config roots. This records content/context identity; it does not authenticate authorship or prove semantic/native equivalence. No app import/export authority accepts these reports. Full strict imported-report validation is still required before any future app import route.

Input adds `configRoots` to the prior explicit source set: exactly `{files,mounts,configRoots}`. Root records are `{file,root}` with a selected source filename and package-relative root. Root metadata rejects accessors, extra fields, unknown/duplicate owners and unsafe paths. Shared `createSourceContext` snapshots/fixes source identities, exposes immutable copies, and prevents relative function paths from escaping an explicitly declared config root. It performs no filesystem access. Existing dependency reports remain byte-content equivalent on all five prior fixtures.

Limits add 240 characters per identifier, bounded 240-character literal source-path fields, 32,768 tokens/file, 131,072 aggregate tokens, depth 64, 4,096 config classes, 8,192 properties, 2,048 registration candidates, 8,192 lexical calls, 16,384 aggregate candidate references and an 8 MiB compact report; existing source budgets also apply. Over-limit inputs reject rather than publishing partial analyses. Lexical syntax failures have visible source findings and file coverage status rather than silently asserting successful parsing.

The new registration profile uses the existing bounded Node-worker runner: 15-second default deadline, explicit cancellation, 256 MiB old-generation ceiling and awaited termination. Profile names select two hard-coded worker entries; arbitrary worker paths and coercing profile objects are rejected. Worker threads isolate main-thread work, not arbitrary code security. Sources remain strings and are never evaluated. The new registrations CLI shares bounded UTF-8 input, source-byte rechecks and exclusive report creation with the dependency CLI. The default dependency CLI input and output contract remains unchanged. New registration results remain separate from the older seven-analysis review bundle.

The author-operated in-app conversion workflow, native adapters and all existing roadmap goals remain additive.
